## 正文

前几天要给同事传一段 2.3 GB 的录屏素材，过程大概是这样的：

微信传不了，超过 1 GB 直接拒绝；网盘让我先上传，上传 40 分钟，对方下载还要会员解压；用网盘分享链接，对方打开先弹注册框。

最后我是拿移动硬盘拷的。

这事本身不新鲜，但那天我突然想：**如果两个浏览器能直接对话，中间那些环节是不是全可以省掉？**

于是我做了个小工具，叫 SixDrop。打开网页，选文件，拿到一个 6 位取件码；对方打开同一个网页，输入这 6 位码，两个浏览器就建立了点对点连接，文件从我的机器直接流到他的机器——**不经过任何服务器**。

上线地址是 sixdrop.dev，代码公开在 GitHub 上。下面讲讲它是怎么做出来的，以及真正动手之后才会遇到的问题。

## 为什么是「6 位码」而不是「链接」

最直接的做法是生成一个分享链接，复制粘贴给对方。但实际用下来，链接有几个麻烦：

- 微信里点陌生链接会弹风险提示，对方第一反应是「这是不是钓鱼」
- 链接很长，口头说不清楚
- 群聊里发出去，谁都能点

6 位码不一样，它可以**口述**：「取件码 8 K 3 M 7 Q」。对方打开网页输入就行，不用点任何链接。

技术上就是一个房间号，去掉了容易看错的 `0 1 I O`，剩 32 个字符取 6 位，大约 10 亿种组合，房间 5 分钟内没人进来就自动回收。

这个设计后来被证明是对的——真正用起来的时候，大家几乎都是「打电话/发语音说一串码」，而不是发链接。

## 核心技术：WebRTC DataChannel

要让两个浏览器直接传数据，能用的是 WebRTC 的 DataChannel。它底层是 SCTP over DTLS，特点是**可靠、有序、加密**，本身就是为传数据设计的，不是视频通话那种不可靠流。

整个链路是这样：

```
发送方                          信令服务器                    接收方
  │                                │                          │
  │ 1. 建房，拿到 6 位码 ─────────► │                          │
  │                                │ ◄──── 2. 输入取件码 ──────│
  │ 3. SDP offer ────────────────► │ ────────────────────────►│
  │ ◄──────────────────── SDP answer│ ◄────────────────────────│
  │                                │                          │
  │ ◄══════════ DataChannel（DTLS 加密）══════════════════════►│
  │            文件字节直接对传，服务器完全不参与                │
```

信令服务器只负责交换两串文本（SDP）和网络候选地址，**碰不到任何一个文件字节**。

信令本身我用了 Cloudflare Workers + Durable Objects：一个房间对应一个 DO 实例，用 WebSocket 转发消息。选它的原因很朴素——**免费额度够用，成本是 0**。

## 一个反直觉的决定：不装 TURN 服务器

WebRTC 能不能连上，取决于两端能不能「打洞」穿过各自的 NAT。

现实中，公司网、校园网、部分 4G/5G 都是**对称 NAT**，这种情况打洞几乎必然失败。业界标准解法是配一台 TURN 服务器做中继——**所有流量绕服务器转一圈**。

我没装。原因有两个：

**一是成本。** TURN 是按流量计费的，传 1 GB 就烧 1 GB 的服务器带宽。一个免费工具，只要有人传大文件，账单立刻失控。

**二是产品定位。** 如果最后所有流量都走服务器，那这个工具和网盘的区别就只剩「不需要登录」了，那我做它干嘛？

所以我的选择是：**打不通就明说，给用户两条路。**

一条是换个网络重试——手机热点通常最快验证，因为移动网络和家宽的 NAT 类型往往不同。另一条是「改用中转」：文件临时传到 Cloudflare R2，生成链接给对方，24 小时后自动删除，也可以手动立即删。

这是明码标价的妥协：**默认不经过服务器，实在打不通才走，而且走的时候告诉你。**

## 打不通的时候，得让用户知道为什么

最初的失败页只写「连接失败，请重试」。用户看到这句话只会反复点重试。

后来加了一段诊断，把收集到的候选地址按类型统计：

```
候选：host 6 · srflx 2 · relay 0 — 有公网映射但对不上，典型对称 NAT
```

这三个数字的含义：

- `host` 是本机地址，`srflx` 是通过 STUN 拿到的公网映射，`relay` 是中继候选
- **`srflx` 是 0**：说明 STUN 都没打通，多半是网络禁了 UDP，换 Wi-Fi 试试
- **`srflx` 有但连不上**：有公网映射却配不上对，基本就是对称 NAT，只能换网络

有了这行字，用户至少知道该干嘛，而不是干瞪眼。

## 传输：分块和背压

DataChannel 不能一次 `send` 一个 2 GB 的 Blob，得自己切块。

我用的是 256 KiB 一块，并且按 `pc.sctp.maxMessageSize` 收窄——Chrome/Edge 给 256 KiB，老的实现只有 64 KiB，写死会直接抛异常。

比切块更容易出错的是**背压**。如果循环里不停地 `send`，浏览器会把数据堆在内存里，几百兆之后页面就卡死了。所以每发一块之前检查 `dc.bufferedAmount`，超过 8 MiB 就等 `bufferedamountlow` 事件再继续。

```
bufferedAmount < 8 MiB  →  直接发
bufferedAmount ≥ 8 MiB  →  挂起，等水位降到阈值以下
```

这段代码写完，传输速度反而更稳定了——之前是「猛发一阵然后卡住」，现在是匀速。

## 真正麻烦的不是传输，是写文件

接收端收到数据块，得落到磁盘上。这里浏览器之间的差异非常大：

**Chrome / Edge** 有 `showSaveFilePicker` 和 `showDirectoryPicker`，可以拿到文件句柄，**边收边写**，内存占用恒定。多文件的时候让对方选一个文件夹，所有文件自动存进去。

**Firefox / Safari** 没有这套 API，只能先把所有分片攒在内存里，最后拼成一个 Blob 触发下载。传 2 GB 就是 2 GB 内存，基本必炸。

这个问题没法用代码绕过，只能在 UI 上明确告诉用户：不支持流式写入的浏览器，建议单文件别超过 1 GB。

## 一个容易被忽略的安全问题：中间人

信令服务器是我自己的，理论上它可以偷偷替换 SDP，把连接导到别处。

WebRTC 本身有 DTLS 加密，但它只保证「和对面加密通信」，不保证「对面就是我以为的那个人」。

所以两端连接建立后，各取一次 DTLS 证书的指纹，取前 8 位显示出来，**让两个人对一眼**：

```
校验码 2FCF88AD  双方对照一致，说明中间人无法替换
```

这一行字的成本很低，但它把「信任服务器」变成了「信任自己眼睛」。

## 七个只有真做了才会踩到的坑

**1. 静态资源的 301 把分享页干掉**

我加了个 `/d/<token>` 的分享页，逻辑是「拿到任意路径就返回首页 HTML」。结果 `fetch('/index.html')` 会被 Cloudflare 的静态资源层**规范化重定向到 `/`**，分享页一打开就跳回首页，看起来像坏了。

改成 `fetch('/')` 就好了。

**2. SVG 文件里的 UTF-8 BOM 让图标被裁**

图标是 SVG，生成 PNG 的时候把它内联进 HTML 渲染。结果每个尺寸的图标**都被裁掉底部 21px**。

查了很久才发现：我用 PowerShell 的 `Set-Content -Encoding utf8` 写文件，它自动加了 BOM。BOM 内联到 HTML 里变成一个不可见字符，浏览器为它建了一个行盒，把 SVG 往下推了 21px——正好是一个默认行高。

在 512px 图标上偏移 4% 看不出来，154px 上就是 12%，一眼就露馅。

**3. 用户不刷新页面，连了新服务端**

改了消息协议之后，还开着旧标签页的用户点按钮毫无反应——因为旧 JS 发的是旧消息类型，新 Worker 直接丢弃。

这是个死结：提示刷新会被误点，自动刷新会丢状态。最后我的做法是**让协议向后兼容**，加上消息队列和自动重连，不再指望用户刷新。

**4. Durable Object 的定时器会提前回收**

房间本来设了 30 分钟过期。结果发现传到一半，房间被回收了，信令断了。

原因是 DO 的 alarm 在连接还活着的时候也会触发。改成「触发时先看还有没有 WebSocket，有就往后顺延」。

**5. 中转模式下的 5 GiB 硬上限**

R2 单次 PUT 最大 5 GiB，超过就得走 multipart。multipart 又有个坑：分片最小 64 MiB，最多 10000 片——所以不能用固定 5 MiB 分片，得根据文件大小算。

**6. 多文件传输时同名覆盖**

接收方选文件夹时，如果连着收两次 `photo.jpg`，第二次会覆盖第一次。加了 `(1)(2)` 的后缀。

**7. 手机切后台，连接就断**

WebRTC 在移动端切到后台会被系统挂起，回来时连接已经断了。这个目前只能提示，没法根治。

## 现在它能做什么

- 多文件传输，接收端选一个文件夹全部存进去
- 传文字：不想传文件的时候，切到「文本」标签，直接发一段话
- 打洞失败时：给出诊断 + 可选的两条路（换网络 / R2 中转）
- 中转的文件：24 小时自动删除，也能「已收到，立即删除」
- 分享页：对方当时不在线，可以先传 R2 生成链接发过去
- 校验码对照、进度、速度、剩余时间

成本：Cloudflare Workers 免费额度 + Durable Objects 免费额度 + R2 的 10 GB 免费存储。目前是 **0 元/月**。

## 说清楚它的局限

不想把话说过头，这几条是真的不行：

- **没有断点续传。** 传一半断了要从头再来。这是下一步想做的。
- **对称 NAT 就是打不通。** 不装 TURN 的代价，只能靠中转绕。
- **Firefox / Safari 大文件不友好。** 内存攒 Blob，1 GB 以上基本没戏。
- **手机切后台可能断。**
- **速度取决于双方带宽。** 局域网能跑满千兆，跨运营商就看运气。

## 互动准备

评论大概率会问这几个，提前想好回答：

- **「和 LocalSend / Snapdrop 有什么区别？」** → LocalSend 要装应用；Snapdrop 只支持局域网。SixDrop 是跨网络的浏览器直连，且不装 TURN。
- **「开源吗？能自己部署吗？」** → 代码公开在 GitHub，可以看、可以学；目前没有许可证，所以严格说不是「开源」，也请不要直接商用。
- **「文件真的不经过服务器？」** → 直连时确实不经过；打洞失败走中转时会明确提示。
- **「为什么不做断点续传？」** → WebRTC DataChannel 是有序流，续传要先做分片索引和校验，在计划里。
- **「安全吗？」** → DTLS 加密 + 两端指纹对照，中间人无法静默替换。
